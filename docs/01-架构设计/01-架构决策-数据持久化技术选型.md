# 架构决策：数据持久化技术选型

## 1. 背景与现状
用户询问是否需要引入后端数据库（如 MySQL/PostgreSQL）以支持数据落表。
当前项目（LiuliX）定位为 Data Exploration Platform (EDA)，主要技术栈为：
- 计算引擎：**DuckDB-Wasm** (客户端执行)
- 存储现状：本地文件加载，少量 `Dexie.js` (IndexedDB) 使用
- 后端服务：轻量级 Node.js，主要用于 LLM 代理和静态资源服务

## 2. 方案对比

| 维度           | 方案 A: 传统后端数据库 (MySQL/PG)           | 方案 B: Local-First (IndexedDB + OPFS) |
| :------------- | :------------------------------------------ | :------------------------------------- |
| **架构复杂度** | 高 (需维护 API Server, ORM, Auth, Database) | 低 (直接在浏览器操作)                  |
| **数据隐私**   | 低 (用户数据需上传服务器，涉及合规)         | 高 (数据不出用户设备)                  |
| **性能**       | 中 (受限于网络带宽和延迟)                   | 高 (零网络开销，直接内存/本地IO)       |
| **开发成本**   | 高 (需开发全套 CRUD 接口)                   | 低 (复用前端组件状态)                  |
| **匹配度**     | 低 (与 DuckDB-Wasm 本地计算模型冲突)        | 高 (DuckDB 原生支持 OPFS)              |

## 3. 核心建议：Local-First 架构

基于 "MVP 功能闭环优先" 和 "轻量化" 原则，**强烈不建议**引入重型后端数据库。

### 推荐技术栈
1.  **配置/元数据 (Prompts, History, Settings)**
    *   **技术**: **Dexie.js (IndexedDB 封装)**
    *   **理由**: 异步非阻塞，容量大（GB级），支持事务和索引，API 友好。
2.  **大数据集 (CSV, Parquet, User Uploads)**
    *   **技术**: **OPFS (Origin Private File System)**
    *   **理由**: 浏览器原生私有文件系统，性能接近本机应用，DuckDB-Wasm 可直接挂载读取。
3.  **后端服务**
    *   **定位**: 保持 **Stateless Proxy**
    *   **职责**: 仅负责 LLM API 转发、Pyodide 包分发，**不存储任何业务数据**。
