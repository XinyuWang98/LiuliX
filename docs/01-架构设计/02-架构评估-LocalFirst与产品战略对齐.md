# 架构决策：从 Local-First 到 Cloud-Sync 的演进路线

## 1. 战略对齐 (Strategy Alignment)
根据 [产品战略与愿景](../00-必读/07-核心-LiuliX产品战略与愿景.md)，LiuliX 需要同时支持两条演进路线：
1.  **Web 社区线 (To-C)**: 工具 -> 社区 -> 创作者经济 (需账号、跨设备同步、分享)。
2.  **企业协作线 (To-B)**: 离线版 -> 团队版 -> 企业私有部署 (需数据隔离、团队协作、LDAP)。

当前阶段 (MVP) 的架构选择必须能平滑演进到这两种终态，避免未来重构。

## 2. 为什么 "Local-First" 是最佳起手式？

我们需要澄清一个误区：**Local-First 不等于 "永远单机"**。
相反，**Local-First 是实现 "高性能同步" 和 "离线可用" 的最佳基石**。

### 架构演进三步走

| 阶段              | 架构重点     | 数据流向                                   | 关键技术                              | 状态       |
| :---------------- | :----------- | :----------------------------------------- | :------------------------------------ | :--------- |
| **MVP (当前)**    | **本地内核** | `Browser (IndexedDB)` 仅本地               | **Dexie.js** + **OPFS**               | ✅ 正在实施 |
| **V1.5 (社区版)** | **云端同步** | `Browser` <-> `Sync Server` <-> `Cloud DB` | **Supabase / Firebase** (Auth + Sync) | 🔋 预留接口 |
| **V4 (企业版)**   | **私有协作** | `Enterprise Browser` <-> `Private DB`      | **Docker** + **PostgreSQL**           | 🏢 架构兼容 |

### 核心优势
1.  **用户体验**：无论有没有网，App 都能瞬间打开、秒级响应（因为读写本地 DB）。
2.  **即刻落地**：C 端 MVP 马上就能用，无需等待后端开发。
3.  **To-B 兼容**：To-B 客户往往要求 "数据不离网"。Local-First 架构天生支持 "断网使用"，部署时只需把同步目标地址改向企业内网服务器即可。

## 3. 技术实施：为同步做准备

为了确保 V1/V2 能顺利接入账号和同步系统，我们在当前 MVP 阶段的本地数据库设计必须遵守以下 **"Sync-Ready" 规范**：

### A. ID 生成策略
*   ❌ **禁止**：自增主键 (Auto Interface ID, e.g., 1, 2, 3)。同步时会冲突。
*   ✅ **强制**：**UUID (v4)**。确保全球唯一，任何设备生成的 ID 同步到云端都不会冲突。

### B. "最后修改时间" (Last Write Wins)
*   所有表必须包含 `updated_at` 和 `deleted_at` (软删除) 字段。
*   这是实现增量同步 (Delta Sync) 的基础。

### C. 账号预留
*   在 `Settings` 表中预留 `user_id` 字段。
*   MVP 阶段：`user_id` = "local_user" (默认)。
*   V1.5 阶段：用户登录后，更新 `user_id` = "uuid-xxx"，并触发一次全量同步。

## 4. 结论：架构评估
**Local-First 架构** 完全符合 LiuliX 的长期战略愿景。它不仅满足 MVP 的快速发布，更为**跨设备同步** (Web 版特性) 和 **离线高可用** (企业版特性) 提供了最坚实的底层架构。

### 修正后的实施计划
1.  **DB 初始化**：使用 Dexie.js，但 ID 策略改为 UUID。
2.  **Service 层**：封装 CRUD 时，必须维护 `updated_at` 字段。
3.  **后续接入**：V1.5 时引入 Supabase/Firebase 作为 Sync 后端，前端代码改动极小（只需增加 Sync Adapter）。
