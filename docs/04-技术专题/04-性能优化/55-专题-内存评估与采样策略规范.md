# 内存评估与采样策略规范

> **最后更新**: 2026-01-13
> **状态**: ✅ **已定稿 (Finalized)**
> **适用版本**: v1.0+
> **决策依据**: 基于 2026-01-11 百万行数据(1M Rows)端到端压力测试结果，确认此分级策略能有效防止 OOM 并保证用户体验。

本文档定义了 LiuliX 系统在不同用户设备内存环境下的数据处理策略，旨在平衡性能与稳定性，特别针对高性能设备（24GB/32GB+）进行了深度优化。

---

## 策略总览

系统将根据 `performance.memory.jsHeapSizeLimit` 获取浏览器堆内存上限（如不可用则根据 UserAgent 或降级策略估算），将设备划分为 **6 个性能档位**。

每个档位对应不同的资源配额：
1. **内存预算 (RAM Budget)**: 分配给 Pyodide/DuckDB 的最大可用内存比例
2. **Pyodide 最大行数**: 允许加载到 Python 环境进行可视化/计算的最大行数
3. **文件上传限制**: 允许上传处理的 CSV 文件大小上限
4. **最大并发数**: Insight 洞察分析时的 Worker 并行数量

## 6档精细化分级表

| 档位         | 设备内存    | 内存预算 | Pyodide 最大行数 | 文件大小限制 | 并发数 | 场景描述               |
| :----------- | :---------- | :------- | :--------------- | :----------- | :----- | :--------------------- |
| 🔴 **低配**   | < 4GB       | 10%      | 30,000           | 50MB         | 1      | 老旧设备/移动端        |
| 🟠 **标准**   | 4GB - 8GB   | 15%      | 50,000           | 100MB        | 2      | 入门级办公本           |
| 🟡 **主流**   | 8GB - 16GB  | 20%      | 100,000          | 200MB        | 3      | 主流轻薄本 (Air 8G)    |
| 🟢 **高性能** | 16GB - 24GB | 30%      | 300,000          | 500MB        | 4      | 开发者/MacBook Pro 16G |
| 🔵 **旗舰**   | 24GB - 32GB | 35%      | 500,000          | 800MB        | 5      | 高端工作站             |
| 🟣 **极致**   | 32GB+       | 40%      | 800,000          | 1.2GB        | 5      | 顶级配置/Mac Studio    |

## 详细实施规范

### 1. 内存预算计算公式
```typescript
AvailableMemory = SystemMemory * BudgetRatio * SafetyMargin(0.7)
```
* **SafetyMargin 0.7**: 预留 30% 缓冲以应对浏览器其他标签页、插件及 UI 渲染开销。

### 2. 采样与截断策略

#### DuckDB 摄入阶段 (Ingestion)
- **输入**: CSV 文件
- **策略**:
  - 若文件大小 < 文件大小限制: **全量加载**
  - 若文件大小 > 文件大小限制: **拒绝上传** (提示分割文件)
  - 若行数 > 推荐行数 (基于内存动态计算): **自动采样**
- **采样率公式**:
  ```typescript
  RecommendedRows = AvailableMemory / (Columns * 24 bytes)
  SampleRate = RecommendedRows / TotalRows
  ```
  *(注: 24 bytes = 8 bytes double * 3 倍 Pandas/Arrow 开销系数)*

#### Pyodide 计算阶段 (Insight Execution)
- **输入**: DuckDB 查询结果
- **策略**:
  - 若行数 < Pyodide 最大行数: **全量传递**
  - 若行数 > Pyodide 最大行数: **后端截断 (Limit)**
- **注意**: 这里的限制是为了防止浏览器崩溃，DuckDB 中仍保留全量（或采样后的）数据，仅在传给 Python 绘图时做二次截断。

### 3. 并发数控制策略
Insight 分析默认采用并行策略，但为了避免多 Worker 抢占主线程导致 UI 卡顿，严格限制最大并发数。

- **低配/标准 (<8GB)**: 1-2 并发，优先保证主线程响应。
- **高性能 (16GB+)**: 4-5 并发，充分利用多核 CPU。
- **上限**: 锁定为 5，即使 64GB 内存也不超过 5，因为浏览器 Worker 通信开销会边际递减。

## 风险与兜底

| 风险点         | 表现                                   | 兜底机制                                                              |
| :------------- | :------------------------------------- | :-------------------------------------------------------------------- |
| 内存估算过高   | 页面崩溃 (OOM)                         | 监控 `navigator.deviceMemory`，若发生 OOM，下次启动自动降级档位       |
| 浏览器内存限制 | 虽然物理内存大，但浏览器限制单 Tab 4GB | `jsHeapSizeLimit` 通常能读取到限制，若超过 4GB 会被截断，策略自动适配 |
| 多任务竞争     | 用户同时开多个高负载 Tab               | 保留 30% 安全缓冲 (SafetyMargin)                                      |

## 未来规划 (v1.2)
- **基于 OPFS 的核外计算**: 利用 DuckDB 的磁盘交换能力，突破内存限制处理 GB 级数据。
