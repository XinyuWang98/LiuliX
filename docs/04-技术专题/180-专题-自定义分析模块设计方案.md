## 1. 核心愿景 (Vision)

构建一个“**配置与执行分离**”的双核系统：
1.  **后台 (Management Hub)**：专为专家设计的“军火库”。在这里定义 Prompt 模版、编排 n8n 风格的复杂 Workflow。
2.  **前台 (Workbench)**：高效的执行战场。自动跑通预设 Workflow，并通过右侧 Copilot 进行即时战术调整。

---

## 2. 核心架构设计 (Architecture)

### 2.1 模块一：独立配置中心 (The Management Hub)
*改造现有的 `Prompt` 页面，升级为全功能的模版与流程管理平台。*

#### A. Prompt 模版库 (Prompt Library)
*   **功能**：用户勾选、编辑、管理 Prompt 模版。
*   **分类**：
    *   **清洗模版 (Cleaning Prompts)**：如“财务数据标准化”、“电商SKU去重”。
    *   **分析模版 (Analysis Prompts)**：如“SWOT 分析”、“杜邦财务分析”。
*   **操作**：
    *   **Edit**: 编辑 System/User Prompt，插入变量（`{{df.head}}`, `{{columns}}`）。
    *   **Debug**: 上传测试数据，预览 LLM 输出结果。
    *   **Monitor**: 查看该模版的历史调用成功率和耗时。

#### B. 流程编排器 (Workflow Studio)
*   **交互**：**类似 n8n 的节点拖拽式 UI**。
*   **逻辑**：
    *   Node Types: `Trigger (Upload)` -> `Action (Clean: Recipe A)` -> `Action (Analyze: Prompt B)` -> `Output (Report PDF)`.
    *   **Priority 1**: 在这里配置的 Workflow 被视为“第一梯队”，在 Workbench 数据加载后**自动优先执行**。
*   **场景**：用户配置一个“月度审计流”，以后每个月上传数据，系统自动跑完所有步骤并生成报告。

### 2.2 模块二：数据工作台 (The Workbench)
*分析与清洗的主界面。*

#### A. 左侧工作区 (Workspace)
*   **默认行为**：
    *   数据上传后，**立即检查**是否有匹配的 Custom Workflow（来自配置中心）。
    *   如果有，自动执行，并在左侧渲染执行结果卡片（Cleaning Suggestions / Insight Cards）。
    *   如果没有，跑默认的通用分析逻辑。

#### B. 右侧智能助手 (Sidebar Copilot)
*   **定位**：用于处理**非预设**的、即时的分析需求。
*   **模型**：支持与 Local Model (Ollama) 或 Cloud Model 沟通。
*   **交互闭环**：
    1.  **Chating**: 用户在右侧输入：“帮我把所有日期的格式转成 YYYY-MM-DD”。
    2.  **Thinking**: Copilot (Agent) 解析意图，生成代码或建议。
    3.  **Action**: Copilot 将生成的建议**发送给左侧工作区**。
    4.  **Rendering**: 左侧工作区新增一张“清洗建议卡片”，用户点击“执行”即可生效。

## 3. 详细交互设计 (Interaction Flow)

### 3.1 场景一：专家配置“财务审计流”
1.  进入 **设置/Prompt Library** 页面。
2.  新建一个 Workflow，拖入：
    *   `Input Node`: 限制文件名为 `audit_*.xlsx`。
    *   `Cleaning Node`: 引用“财务清洗模版”（去除空行，补全金额）。
    *   `Analysis Node`: 引用“风险评估模版”。
3.  点击 **Save & Activate**。

### 3.2 场景二：日常执行与微调
1.  用户进入 **Workbench**，上传 `audit_2025Q1.xlsx`。
2.  **自动执行**：系统识别文件名匹配，自动运行上述 Workflow。
3.  **结果展示**：左侧出现清洗后的数据表和风险评估报告。
4.  **追加需求**：用户发现还需要看下某个异常值的细节。
5.  **右侧对话**：打开 Sidebar Copilot，输入：“帮我查一下第 3 行这个异常金额的来源”。
6.  **即时响应**：Copilot 生成一段查询 SQL/Python，在左侧渲染为一个新的“临时分析卡片”。

## 4. 技术实现策略

### 4.1 优先级队列 (Priority Queue)
*   `InsightExecutor` 需改造支持优先级：
    *   **Tier 1**: Custom Workflow (User Configured).
    *   **Tier 2**: Context Smart Suggestions (System Default).
    *   **Tier 3**: Copilot Ad-hoc Requests.

### 4.2 消息总线 (Event Bus)
*   实现 Sidebar 到 Workbench 的通信机制：
    *   `eventBus.emit('NEW_SUGGESTION', { type: 'cleaning', payload: ... })`
    *   Workbench 监听事件并动态渲染组件。

## 7. 开发工作量评估 (Workload Assessment)

**整体评估**: 这是一个 **Large (L)** 级别的特性开发，涉及前端复杂交互（拖拽、聊天）和核心业务逻辑重构（执行优先级）。建议分阶段实施。

### 7.1 核心难点 (High Effort Items)
1.  **Workflow Studio (n8n 风格画布)**: 
    *   **难度**: ⭐⭐⭐⭐⭐
    *   **原因**: 实现一个健壮的拖拽式 DAG 编辑器（基于 ReactFlow）且要处理复杂的节点连线与状态校验，前端工程量巨大。
    *   **策略**: MVP 阶段建议先做 **"线性表单模式" (Linear Stepper)**，暂时不支持复杂的条件分支，降低实现成本。
2.  **Copilot Action Protocol**:
    *   **难度**: ⭐⭐⭐⭐
    *   **原因**: 需要定义一套标准的协议，让右侧聊天窗口生成的建议能“无缝”转化为左侧可执行的 React 组件卡片，且要处理上下文同步问题。

### 7.2 模块估算
| 模块          | 功能点                      | 预估复杂度  | 建议排期                |
| :------------ | :-------------------------- | :---------- | :---------------------- |
| **配置中心**  | Prompt Library (CRUD)       | Medium      | Phase 1                 |
|               | Workflow Builder (Canvas)   | **X-Large** | Phase 3 (MVP用表单替代) |
| **Workbench** | 优先级调度逻辑 (Tier 1/2/3) | Medium      | Phase 2                 |
|               | Sidebar Chat UI             | Medium      | Phase 2                 |
|               | Chat-to-Card 渲染协议       | **Large**   | Phase 2                 |

### 7.3 MVP 推荐路径 (Low Hanging Fruit)
为了快速上线并验证价值，建议第一版本缩通过以下方式减负：
1.  **暂缓拖拽**: Workflow 配置使用简单的“步骤列表”形式。
2.  **聚焦 Prompt**: 先把 Prompt Library 做起来，这是最高频的需求。
3.  **Sidebar 基础版**: 先实现对话，"渲染卡片"功能可以先简化为"生成代码块，用户手动复制"。

## 8. 社区商店与商业化设计 (Store & Marketplace Strategy)

为了支持未来的“订阅制收费”与“社区案例分享”，系统需要引入标准的**包管理机制 (Package Management)**。

### 8.1 核心页面：Store Page
*   **定位**：发现与获取优质分析资产的入口。
*   **板块**：
    *   **Featured Workflows**: 官方精选的复杂工作流（如“SaaS 核心指标仪表盘”）。
    *   **Community Cases**: 用户分享的真实案例（"我是如何用这个模版发现财务漏洞的"）。
    *   **Prompt Market**: 细分领域的 Prompt 模版单品（需积分/订阅）。

### 8.2 数据与交互链路
1.  **发布 (Publish)**：
    *   用户在 `Management Hub` 选择一个 Workflow。
    *   点击 `Share to Store`。
    *   系统自动打包为标准格式，并要求填写“案例描述”与“适用数据Schema”。
2.  **获取 (Acquire)**：
    *   用户在 Store 点击 `Get` / `Buy`。
    *   系统**Clone**一份副本到用户的 `Management Hub` -> `Purchased` 文件夹。
    *   **引用机制 (Reference)**：如果该模版随官方升级，用户可选择 `Update`，或 `Fork` 出自己的修改版。

### 8.3 技术实现：兼容性与格式 (Compatibility)

**为了实现跨版本的稳定调用，必须定义严格的 Schema 协议。**

#### A. 统一包格式 (The `.liulix` Package)
所有的 Prompt、Code、Workflow 都被封装为一个 JSON 包：

```json
{
  "manifest": {
    "id": "com.user.finance_audit",
    "version": "1.0.2",
    "min_engine_version": "2.1.0", // 依赖的 LiuliX 引擎版本
    "pricing": { "type": "subscription", "plan": "pro" }
  },
  "content": {
    "workflow_graph": { ... }, // n8n style graph
    "prompts": { ... },
    "scripts": { ... }
  },
  "interface": {
    "input_schema": ["date", "amount", "category"], // 声明需要的数据列
    "output_mock": { ... } // 用于预览效果的 Mock 数据
  }
}
```

#### B. 向后兼容策略 (Backward Compatibility)
*   **版本锁 (Version Locking)**：用户下载的是 `v1.0.2` 的快照。即使社区更新到了 `v2.0`，用户的本地版本不受影响，除非手动点击“更新”。
*   **引擎适配层 (Adapter Layer)**：
    *   如果 LiuliX 引擎升级（比如 Python 环境从 3.11 升到 3.12），核心层会提供 `LegacyExecutor` 来运行旧版包，或者在加载时提示“此模版需要迁移”。

### 8.4 安全沙箱 (Security for Shared Code)
社区分享的 Workflow 可能包含恶意的 Python 代码。
*   **审核机制**: 上架 Store 前需经过系统静态扫描 (AST Analysis) + 人工审核。
*   **运行时限制**:
    *   **Network Ban**: 社区包里的 UDF **默认禁止**网络请求（防止偷数据）。
    *   **Data Scope**: 只能读取当前被显式传入的那个 Table View，无法读取系统其他数据。

## 9. 战略实施规划与 Feature Flags 设计

参考 [07-核心-LiuliX产品战略与愿景.md](../00-必读/07-核心-LiuliX产品战略与愿景.md)，我们将本方案拆解为跨越 **Phase 2 (增长期)** 到 **Phase 3 (平台期)** 的三个里程碑。

每个功能点都必须通过 **Feature Flag** 控制，确保“小步快跑，按需开启”。

### 9.1 里程碑 1: 专家工具箱 (Phase 2.1 - Q2)
*   **目标**：满足由“MVP积累的种子用户”中的专家群体，提供基础的自定义能力。
*   **核心交付**：Prompt Library (CRUD) + Workbench Sidebar (Chat Only)。

| 功能模块           | Feature Flag (key)            | 默认状态        | 描述                                 |
| :----------------- | :---------------------------- | :-------------- | :----------------------------------- |
| **Prompt Library** | `ENABLE_PROMPT_LIBRARY`       | `false` (Alpha) | 允许用户增删改查 Prompt 模版         |
| **Module Runner**  | `ENABLE_CUSTOM_MODULE_RUNNER` | `true`          | 底层运行时，允许执行自定义 JSON 配置 |
| **Sidebar UI**     | `ENABLE_WORKBENCH_SIDEBAR`    | `false`         | 右侧聊天窗口的基础框架               |
| **Local LLM**      | `ENABLE_LOCAL_LLM_CHAT`       | `false`         | 允许 Sidebar 连接 Ollama             |

### 9.2 里程碑 2: 自动化与联动 (Phase 2.2 - Q3)
*   **目标**：打通“聊”与“做”的壁垒，实现 Agent 驱动的分析。
*   **核心交付**：Workflow Config (表单版) + Chat-to-Card protocol。

| 功能模块           | Feature Flag (key)               | 默认状态 | 描述                                        |
| :----------------- | :------------------------------- | :------- | :------------------------------------------ |
| **Workflow API**   | `ENABLE_WORKFLOW_PRIORITY`       | `false`  | 改造 Executor，优先执行 Configured Workflow |
| **Chat Action**    | `ENABLE_CHAT_TO_CARD`            | `false`  | 允许 Chat 消息渲染为 UI 卡片                |
| **Simple Builder** | `ENABLE_SIMPLE_WORKFLOW_BUILDER` | `false`  | 基于表单的线性流程配置器                    |

### 9.3 里程碑 3: 商业化闭环 (Phase 2.5 - Q4)
*   **目标**：在复杂的可视化编辑器上线前，先行跑通商业模式。
*   **策略**: **Store 前置**。即使没有拖拽编辑器，用户依然可以在 Store 购买/下载 "Prompt 模版" 和 "配置版 Workflow"。
*   **核心交付**：Community Store Beta + Subscription Payment。

| 功能模块         | Feature Flag (key)          | 默认状态 | 描述                     |
| :--------------- | :-------------------------- | :------- | :----------------------- |
| **Store Access** | `ENABLE_COMMUNITY_STORE`    | `false`  | 访问社区商店的入口       |
| **Payment**      | `ENABLE_SUBSCRIPTION_CHECK` | `false`  | 商业化鉴权与支付网关集成 |

### 9.4 里程碑 4: 终极形态 (Phase 3.0 - Next Year)
*   **目标**：提供 n8n 级别的极致编排体验，降低小白用户门槛。
*   **核心交付**：Visual DAG Editor (拖拽画布)。

| 功能模块          | Feature Flag (key)         | 默认状态 | 描述                          |
| :---------------- | :------------------------- | :------- | :---------------------------- |
| **Visual Studio** | `ENABLE_VISUAL_DAG_EDITOR` | `false`  | n8n 风格的拖拽画布 (X-Large)  |
| **Sandboxing**    | `ENABLE_STRICT_SANDBOX`    | `true`   | 强制开启第三方包的网络/IO限制 |

### 9.5 灰度策略 (Rollout Strategy)
1.  **Dev/Internal**: 开启所有 `Alpha` flags。
2.  **Beta Users**: 开启 `ENABLE_PROMPT_LIBRARY` 和 `ENABLE_WORKBENCH_SIDEBAR`，收集反馈。
3.  **Public Release**: 待 Beta 稳定后，移除 flag 或设为 `true`。
