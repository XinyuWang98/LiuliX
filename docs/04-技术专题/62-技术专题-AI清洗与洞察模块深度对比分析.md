# 62-技术专题-AI清洗与洞察模块深度对比分析

**创建时间**: 2025-12-24  
**关联模块**: `aiCleaningService`, `useInsightLoaderV2`

---

## 1. 核心评估结论

经过代码级审计，我们确认 **AI清洗建议 (Cleaning)** 和 **AI洞察建议 (Insights)** 是两套**完全独立**的逻辑体系。尽管它们都涉及 "DuckDB查询 -> 数据脱敏 -> AI Prompt" 的流程，但在具体实现、架构成熟度及隐私策略上存在显著差异。

### 📊 对比总览

| 维度 | 🛡️ AI清洗模块 (Cleaning) | 🧠 AI洞察模块 (Insights) |
| :--- | :--- | :--- |
| **逻辑入口** | `useSuggestionGeneration.ts` -> `aiCleaningService.ts` | `useInsightLoaderV2.ts` |
| **数据源健壮性** | **曾有缺陷** (依赖上游组件传递状态，易丢失) | **健壮** (自带 Fail-safe 机制，上游为空时主动兜底查询) |
| **脱敏策略** | **局部遮掩 (Masking)** <br> 使用 `dataSanitizer.ts` <br> 例：`138****0000`, `张*` <br> **目的**：保留格式供AI识别，但隐藏PII | **截断/开关 (Truncation/Toggle)** <br> 使用 `dataPrivacy.ts` <br> **策略**：若开启隐私模式，直接**不传**任何样本数据，仅传列名 <br> **目的**：彻底物理隔离 |
| **架构成熟度** | **V1 架构** <br> 简单的 Hook-Service 模式 | **V2 架构** <br> 集成了双模式 (Local/Cloud)、质量门控、资源限制、进度反馈 |
| **Prompt 目标** | 关注**数据质量** (空值、异常、格式错误) | 关注**业务价值** (趋势、分布、图表生成) |

## 2. 详细代码对比

### 2.1 数据源获取 (Data Sourcing)

*   **Cleaning (旧模式)**:
    强烈依赖 `activeFile.data.columns`。如果上游组件（如 LeftSidebar）传递状态失败，清洗模块就会拿到空数组，导致 Prompt 列信息丢失（即 Issue #19）。
    > *修复状态：已通过在 Hook 内部增加 `duckdb.getColumnStats` 兜底修复。*

*   **Insights (新模式)**:
    在 `useInsightLoaderV2.ts` 中内置了完整的检查逻辑：
    ```typescript
    // 🛡️ 健壮的兜底逻辑
    if (有效列名.length === 0 && tableName) {
        const describeResult = await engine.runQuery(`DESCRIBE ${tableName}`);
        有效列名 = describeResult.map(...)
    }
    ```
    即使上游传错，它也能自愈。

### 2.2 脱敏实现 (Privacy Implementation)

这是两个模块最大的代码差异点：

*   **Cleaning (`dataSanitizer.ts`)**:
    *   **逻辑**：它认为 AI 需要看到数据的“样子”才能判断清洗规则（例如：是 `yyyy-mm-dd` 还是 `dd/mm/yyyy`）。
    *   **做法**：保留数据样本，但对敏感字段（手机、邮箱、身份证）进行字符级替换（Masking）。
    *   **结果**：AI 看到的是 `139****8888`。

*   **Insights (`dataPrivacy.ts`)**:
    *   **逻辑**：它关注的是列名和统计分布，通常不需要具体那一行的值。
    *   **做法**：提供 `PrivacyMode` 开关。如果为 `auto_sanitize`（默认），则 `sampleData` 参数直接置为空数组 `[]`。
    *   **结果**：AI 根本看不到任何一行具体数据，完全物理隔离。

### 2.3 架构设计 (Architecture)

*   **Cleaning**:
    *   单体式 Prompt 构建。
    *   直接调用 `askAI`。
    *   缺乏质量评估后处理。

*   **Insights (V2)**:
    *   **双模式支持**：自动判断显存，支持切换到 Local LLM (WebGPU)。
    *   **质量门控 (Quality Gate)**：解析 AI 结果后，会经过 `batchValidateInsights` 评分，低于阈值的建议会被丢弃或降级。
    *   **进度反馈**：细粒度的进度条状态管理。

## 3. 复用性评估与建议

### ❓ 是否应该合并代码？

**短期建议：保持现状。**
虽然存在部分逻辑重叠（如 DuckDB 连接、采样查询），但两个模块的**业务目标**和**隐私假设**差异过大：
*   清洗模块**必须**看样本（否则无法纠正格式）。
*   洞察模块**最好别**看样本（为了最大化安全）。

强行合并会产生复杂的 `if (mode === 'cleaning')` 分支逻辑，降低代码可维护性。

### 🚀 长期重构计划 (Long-term Plan)

我们建议在未来实施 **"Common Data Preparation Layer" (公共数据准备层)** 的重构：

1.  **提取 Hook**: `useDataPreparation(tableName, options)`
    *   统一负责检查 Columns 完整性（带兜底）。
    *   统一负责执行 Sampling（采样）。
    *   统一负责 Fetch Stats（统计）。

2.  **统一脱敏管道**:
    *   将 `dataSanitizer` 和 `dataPrivacy` 合并为 `PrivacyGuard` 类。
    *   支持策略模式：`MaskingStrategy` (用于清洗) vs `TruncationStrategy` (用于洞察)。

3.  **架构升级**:
    *   将清洗模块也升级到 V2 架构，接入 `QualityGate`，让 AI 清洗建议也能经过代码规则校验后再展示给用户。

---

## 4. 结论

**AI 洞察模块 (Insights)** 代表了系统目前更高的架构水平和更严格的健壮性标准。
**AI 清洗模块 (Cleaning)** 虽然通过修复已解决稳定性问题，但架构上仍属于上一代设计。未来的技术债务偿还应侧重于将清洗模块“升级”到 V2 架构体系中。
