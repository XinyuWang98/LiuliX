# Google Antigravity 全局开发规则 (v2026.02.13-Updated-v5)

## **核心铁律（最高优先级）**

1. **样式变量强制化**  
   所有像素值、颜色、间距、字体大小、圆角、阴影、行高、边框粗细，必须使用 `:root` 中已定义的 CSS 变量。出现任何硬编码直接视为严重错误。

2. **国际化强制化**  
   所有用户可见文字、错误提示、弹窗文案、按钮文字，必须走 i18n（`t('xxx')`），禁止硬编码字符串。

3. **中文注释与命名**  
   所有注释、日志信息必须用中文。

4. **拒绝魔法数字**  
   禁止出现魔法数字，所有固定值必须定义为 `const` 并命名。

5. **拒绝内联样式**  
   禁止内联 `style` 写死颜色、尺寸、边框，一律用 `className` + CSS 变量。

6. **目录规范**  
   所有新文件必须放在正确目录，禁止乱扔。

7. **文件变更追踪**  
   每次文件变更必须在 `01-核心-项目概览与现状.md` 更新，格式严格一致，需要维护文件树、最新变更。

8. **功能优先，UI/UX 次之（MVP 阶段铁律）**  
   MVP阶段优先功能闭环，UI/UX 只要求“能用、不挡路”。

9. **强制小步快跑测试**  
   每完成最小功能点，必须立即浏览器验证并报告。

10. **强制结构化错误复盘与文档归档**  
    遇报错必须输出【错误分析卡片】并写入 `51-管理-错误日志记录.md`。

11. **强制文件行数上限（新增铁律）**  
    所有文件（除CSS文件和i18n配置文件外）输出代码行数不得超过500行（包括空行和注释）。  
    若编辑后文件行数超过500行，禁止直接变更当前代码，必须先执行以下流程：  
    * **Step 1：分析文件信息**  
      输出【文件分析卡片】，格式如下：  
      * **文件路径**：src/xxx/yyy.ts  
      * **当前行数**：523行  
      * **主要逻辑**：(简述文件核心功能)  
      * **行数超标原因**：(组件太大 / 逻辑太集中 / 缺少拆分)  
      * **拆分建议**：  
        - 方案1：将XX函数提取为独立utils模块  
        - 方案2：将UI组件拆分为A/B/C三个子组件  
        - 方案3：将状态管理移到Context/Hook  
    * **Step 2：等待用户确认拆分方案**  
      必须询问用户：“请选择拆分方案，或提供新方案”  
      未经用户确认，禁止直接修改代码。  
    * **Step 3：执行拆分**  
      根据确认方案，逐步拆分文件（每次只改一个文件，行数控制在500以内）。  
      拆分后，必须在 `01-核心-项目概览与现状.md` 中记录：  
      【文件拆分】 src/xxx/yyy.ts (523行 → 拆分为 src/xxx/yyy.ts + src/utils/zzz.ts + src/components/aaa.tsx)  
    * **Step 4：文档归档**  
      将分析卡片追加写入 `53-管理-文件拆分日志.md`（文件不存在则创建）。  
    **违背规则**：若直接输出超过500行的代码，视为回复无效，必须重写。

12. **强制防重复踩坑与上下文丢失（新增铁律）**  
    所有代码修改或重构时，必须严格执行上下文完整性检查，禁止因重构导致历史数据/状态丢失。  
    若出现“上下文丢失”（如表名变更、File对象丢失、useEffect依赖缺失、tableName未监听等），**禁止直接修复**，必须先执行以下流程：  

    * **Step 1：输出【上下文丢失分析卡片】**  
      * **场景**：当前操作流程  
      * **丢失内容**：具体丢失的部分  
      * **原因分析**：为何丢失  
      * **解决方案**：  
        - 方案1：...  
        - 方案2：...  
      * **策略标签**：`#上下文丢失` `#useEffect依赖缺失` `#File对象丢失` `#表名变更`  

    * **Step 2：等待用户确认**  
      必须询问用户：“请选择解决方案，或提供新方案”。未经确认，禁止直接修改代码。  

    * **Step 3：执行修复**  
      根据确认方案修复，并在 `01-核心-项目概览与现状.md` 记录：  
      `【上下文修复】 src/xxx/yyy.tsx (tableName 丢失 → 添加 useEffect 监听 + JSON 回退)`  

    * **Step 4：文档归档**  
      将分析卡片追加写入 `52-管理-上下文丢失追踪.md`（文件不存在则创建）。  

    **违背规则**：若直接修复上下文丢失问题（未输出分析卡片），视为回复无效，必须重写。

13. **文档归类强制化（新增铁律）**

    所有markdown文档必须遵守6大分类体系和命名规则。

    **核心规则**：
    1. **禁止根目录创建**：除README.md和📚文档导航.md外，禁止在根目录创建任何markdown文档
    2. **强制命名格式**：`序号-类别-中文名称.md`
    3. **必须归类**：所有文档必须放入docs/下的6大分类目录之一
    4. **新建必更新**：每次新建文档后必须更新📚文档导航.md

    **6大分类**：
    - 00-必读 (01-09): 核心文档
    - 01-架构设计 (11-19): 时序图、流程
    - 02-开发日志 (21-29): 功能开发记录
    - 03-测试验证 (31-39): 测试报告
    - 04-技术专题 (41-49): 深度分析
    - 05-项目管理 (51-59): 错误日志、追踪

    **详细规则**：参见 [docs/00-必读/📖文档归类维护规则-Agent必读.md](cci:7://file:///c:/Users/86177/Desktop/DataPrism_antigravity/docs/00-%E5%BF%85%E8%AF%BB/%F0%9F%93%96%E6%96%87%E6%A1%A3%E5%BD%92%E7%B1%BB%E7%BB%B4%E6%8A%A4%E8%A7%84%E5%88%99-Agent%E5%BF%85%E8%AF%BB.md:0:0-0:0)

    **违背规则**：若在根目录或docs/根目录创建markdown文档，必须在24小时内归类或删除。

14. **Markdown 文档中文强制化（新增铁律）**
    所有输出的 Markdown 文档（包括 Artifacts、任务清单、日志、分析报告等）必须使用**中文**编写。
    *   **Artifacts**: task.md, implementation_plan.md 等文件的 Summary, Description, Body 必须全中文。
    *   **异常**: 代码块中的代码原本是英文的可以保留（但注释必须中文），专有名词（如 React, Hook）可保留英文。

15. **日志规范强制化(新增铁律)**  
    所有日志必须使用 `logger` 工具,格式为 `[服务名] 操作描述`,禁止裸 `console.log`。
    **标准服务名**:
    - AI服务、DuckDB、数据清洗、数据分析、文件管理、Python、UI
    **禁止事项**:
    - ❌ "正在"等冗余词
    - ❌ 过多emoji (🎯✅🔍)
    - ❌ 中英混用
    - ❌ Step 1/2/3标记
    - ❌ 服务名不一致
    **使用方式**:
    ```typescript
    import { logger } from '@/utils/logger';
    logger.log('DuckDB', '表创建完成', { count: 3, duration: 100 });
    logger.group('AI服务', '流程标题');
    // ... 流程步骤
    logger.groupEnd();
    ```

16. **文档修改许可强制化（新增铁律）**  
    **严格禁止**在未获得用户明确确认的情况下，擅自修改任何项目文档（`docs/` 下的所有 Markdown 文件）。
    - **范围**：所有 `docs/` 目录下的设计文档、PRD、说明文档。
    - **Artifacts 除外**：`task.md`、`implementation_plan.md` 等 Agent 过程性文件可以自动更新。
    - **流程**：
        1. 在对话中明确提出：“我建议更新文档 X，内容为 Y...”
        2. 等待用户回复“同意”、“确认”或类似肯定指令。
        3. 仅在获得授权后，才能调用 `write_to_file` 或 `replace_file_content` 修改文档。
    - **违背规则**：若擅自修改文档，视为严重违规，必须立即回滚。
    
17. **强制代码复用铁律（新增）**
    所有任务开展前必须确认是否已有现成代码可复用，有可复用的代码优先复用，**严禁重复造轮子**
    - **流程**：
      1. 搜：grep_search搜索现有组件/样式/Hook/业务逻辑
      2. 问：发现可复用资源 → 询问用户确认
      3. 用：直接使用，禁止复制粘贴
    - **常见场景速查：**：
      - Logo/品牌名 → <Logo /> 组件
      - 颜色/间距/字体 → CSS变量 var(--*)
      - 文案 → i18n 
      - t('key')
      - 数据/逻辑 → Hook/Utils/Service
    - **违背规则**：
      发现重复代码 → 立即停止、删除、重写
      记录到`51-管理-错误日志记录.md`

18. **强制 CSS Token 化与视觉合规 (新增铁律)**

    *   **拒绝硬编码**：严禁在 CSS/TSX 中通过 Hex/RGB 手写颜色或像素值（如 `#FFFFFF`, `16px`）。必须使用 `src/styles/tokens/` 定义的 CSS 变量 (如 `var(--text-primary)`, `var(--radius-xl`)。
    *   **拒绝私自 `:root`**：严禁在组件 CSS 中重新定义 `:root`，必须复用全局 Token。
    *   **强制查阅规范**：涉及样式修改时，必须先读取 `docs/00-必读/08-核心-开发设计规范.md` 和 `docs/01-架构设计/33-设计-CSS变量速查.md`。
    *   **玻璃态分级**：模态框必须使用 `vignette` (暗角) + `ultra` (高模糊) 组合，确保 "Ascension" 主题统一。

## **开发流程（必须严格遵守）**

1. **强制先检查报错**：任何修改前，必须先完整阅读当前 IDE 所有报错信息（Problems 面板），并优先修复所有红线错误。只修复报错，不加新功能。修复完必须告诉我“所有报错已清零”。如果没报错，才继续下一步。
2. **强制浏览器验证**：每修复或修改完一个文件，必须手动打开浏览器刷新页面 + F12 检查控制台和 Elements，无任何错误/警告才算通过。必须告诉我“浏览器验证通过，无报错”。
3. 每步完成后必须手动刷新页面验证效果，不准只看预览。
4. **整体流程**：**先思考&Planning** → 提请审核 → 基于全局规则分解任务 → 备份当前文件 → 修改 → **遇错先出分析卡片并写入 `51-管理-错误日志记录.md`** → 浏览器验证 → F12 检查报错 → 修复 → 每改完一个文件必须告诉我“本文件已验证通过” → 再继续下一个。

* 复杂流程使用 `console.group` 分组展示
