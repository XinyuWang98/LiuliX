# 上下文丢失分析卡片：清洗执行逻辑重构 (#21)

## 1. 场景
从 **"本地模板构建SQL (`buildCleaningSQL`)"** 切换为 **"直接执行AI生成的SQL (`suggestion.sql`)"**。

## 2. 丢失内容与风险分析
| 丢失风险点 | 严重性 | 说明 |
| :--- | :--- | :--- |
| **表名占位符上下文** | High | AI 生成的 SQL 包含 `__TABLE_NAME__` 占位符。如果直接执行而忘记替换，会导致 SQL 语法错误。本地模板 `buildCleaningSQL` 内部可能也处理了替换，或者在外部处理了。需要确认替换逻辑的位置。 |
| **参数安全性** | Medium | 本地模板是强类型的（`drop_column(colName)`），绝对安全。AI SQL 是字符串，虽然经过了 `validateSQLSafety`，但仍需确保它不会对其余表（如非 `_working` 表）进行操作。 |
| **Dry Run 状态一致性** | High | 之前的 Dry Run 是基于 AI SQL 跑的。现在执行也基于 AI SQL。理论上一致性**变好**了。但如果 AI SQL 依赖某些临时上下文（如 `CREATE TEMP TABLE`），由于连接池或会话隔离，可能会失败。 |

## 3. 解决方案
### 方案 A：完整透传与替换（推荐）
1.  **Mapping**: 在 `aiCleaningService` 中，确保保留 AI SQL 中的 `__TABLE_NAME__` 占位符不变。
2.  **Exec**: 在 `useCleaningExecution` 中，获取当前真实的 `tableName` (如 `t_12345_working`)，然后执行 `sql.replace(/__TABLE_NAME__/g, tableName)`。
3.  **Fallback**: 为了防止 AI 偶尔未返回 SQL（虽然有校验），保留 `buildCleaningSQL` 作为最后的兜底。

**【执行记录】**
- ✅ **已修复 (2025-12-25)**
- **Prompt**: 修改 `prompts/cleaningSuggestions.ts` 强制 AI 使用 `__TABLE_NAME__`。
- **Service**: 修改 `aiCleaningService.ts`，在 Validation/DryRun 前临时替换，返回时透传占位符。
- **Execution**: 确认 `useCleaningExecution.ts` 在执行前和记录证据前正确替换 `__TABLE_NAME__` 为真实表名。

### 方案 B：仅UI展示，执行仍用模板（否决）
用户明确反对。必须保证“所见即所得”。

## 4. 策略标签
`#上下文一致性` `#SQL注入防御` `#SourceOfTruth`

# 上下文丢失分析卡片：AI请求队列调整排查 (#22)

## 1. 场景
排查AI请求队列机制，验证是否因队列策略不当导致API模式并发性能下降或Key冲突。

## 2. 丢失内容与风险分析
| 丢失风险点 | 严重性 | 说明 |
| :--- | :--- | :--- |
| **并发上下文限制** | High | 如果错误地将 `LocalModelQueue` (串行) 应用于 API 请求，将导致后端双Key带来的并发优势丢失，AI清洗和洞察无法同时进行，严重影响体验。 |
| **API Key隔离性** | Medium | 需要确认前端是否混用了清洗和洞察的请求通道。如果混用，可能导致后端Key配额计算错误或权限越界。 |

## 3. 现状确认 (Correct Context)
经排查代码 (`server/index.js`, `aiService.ts`, `localLLMService.ts`)：
1.  **API模式**：独立使用 `ky` 发送请求，**无队列限制**，天然支持并发。后端已正确拆分为 `/api/proxy/deepseek-cleaning` 和 `/api/proxy/deepseek-insight` 双通道，各自绑定独立 API Key。
2.  **本地模式**：使用 `LocalModelQueue` 进行**严格串行控制**，有效保护了 GPU 显存不崩溃。

## 4. 解决方案
**维持现状 (Status Quo)**
不需要修改任何代码。现有架构已经完美符合“本地串行保安全，API并发提效率”的设计目标。

## 5. 策略标签
`#架构一致性` `#并发控制` `#双Key隔离`
