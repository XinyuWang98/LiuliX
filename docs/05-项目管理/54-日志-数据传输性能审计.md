# 📊 数据传输性能审计日志

## 1. 审计背景
用户反馈大文件上传时存在性能瓶颈，怀疑 **JS -> Pyodide 数据传输** 中的 JSON 序列化是主要原因。本审计旨在量化 `JSON.stringify` + 字符串转义在 Mega 级数据集下的性能开销。

## 2. 审计对象
- **代码文件**: `src/services/skills/modeExecutor.ts`
- **核心逻辑**: 
    1. DuckDB 查询结果 -> `JSON.stringify` (序列化)
    2. Regex Replace -> Python 字符串转义
    3. Pyodide `runPython` -> 加载数据
- **测试环境**: 模拟 Mega 数据集 (600,000 行 x 15 列)

## 3. 测试方法与脚本
使用 `scripts/benchmark_transfer.ts` 模拟核心传输逻辑，隔离其他 IO 干扰。

```typescript
// 核心测试逻辑
const startJson = performance.now();
const jsonStr = JSON.stringify(data);
const jsonDuration = (performance.now() - startJson);

const startEscape = performance.now();
const safeJson = escapeJsonForPython(jsonStr);
const escapeDuration = (performance.now() - startEscape);
```

## 4. 审计结果

| 步骤               | 耗时 (ms)     | 耗时 (s)  | 备注                         |
| :----------------- | :------------ | :-------- | :--------------------------- |
| **JSON.stringify** | 270.73 ms     | 0.27s     | 主要瓶颈，产生 ~182MB 字符串 |
| **Regex Escape**   | 23.01 ms      | 0.02s     | 开销较小                     |
| **JS 总阻塞时间**  | **293.73 ms** | **0.29s** | 主线程完全阻塞               |

> **注**: 此时间不包含 Pyodide 内部 `json.loads()` 的时间 (通常为 JS 侧的 2x-5x)。

## 5. 结论在建议
1.  **现状评估**: 
    *   对于 **Mega (600k行)** 数据集，JS 侧阻塞仅 **0.29s**。
    *   相对于 1.6s 的总导入时间，占比约 18%。
    *   **结论**: JSON 序列化**不是**当前 "卡顿" 的核心原因 (通常 <300ms 用户无感知)。真正的瓶颈可能在 Pyodide 内部的 `json.loads` 或内存分配。

2.  **优化建议**:
    *   **短期 (MVP)**: 维持现状。JSON 通用性最好，0.3s 的阻塞在可接受范围内。
    *   **长期 (Pro)**: 若需支持 500MB+ 数据，建议迁移至 **Apache Arrow** (Zero-copy)，可消除这 0.3s 及 Pyodide 侧的解析开销。
