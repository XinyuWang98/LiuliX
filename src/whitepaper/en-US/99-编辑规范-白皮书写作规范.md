# ✍️ LiuliX Whitepaper Writing Guide

This document defines the writing standards, style guide, and maintenance rules for the LiuliX User Whitepaper. All documents located in the `whitepaper/` directory must follow this specification.

---

## 🎯 Core Goals

The whitepaper faces **end users** directly (not developers), aiming to:
1. **Build Trust**: Transparently explain product mechanisms (Privacy, Security, Cost).
2. **Lower Barrier**: Provide idiot-proof operation guides (e.g., local model deployment).
3. **Convey Values**: Reinforce "Local-First", "Zero Cloud Dependency" product philosophy.

---

## 📝 Naming & File Management

### 1. Naming Rules
- **Format**: `Sequence-Category-Title.md`
- **Sequence Convention**:
  - `01-`: Getting Started
  - `02-`: Policies
  - `03-`: Core Features
  - `10-`: Deep Dive / Architecture
  - `99-`: Meta
- **Examples**:
  - `01-新手教程-Ollama本地部署指南.md` (Keep Chinese filename for consistency)
  - `10-架构原理-本地优先的数据堡垒.md` (Keep Chinese filename for consistency)

### 2. Directory Structure
All user-readable documents must be stored in the root `whitepaper/zh-CN/` or `whitepaper/en-US/` folders.
*(Note: `docs/` is mainly for developers, `whitepaper/` is for users)*

## 🎨 Writing Style (Tone & Voice)

### ✅ Do This (Neutral & Technical)
- **Engineer's Perspective**: Write documents like a Technical Spec. Focus on **Facts** and **Mechanisms**.
- **Restrained**: Use neutral verbs like "Supports", "Provides", "Implements".
- **Objective**: Even for advantages, state the applicable boundaries.
- **Example**:
    - ✅ "Local mode keeps data on the client side."
    - ❌ "Local mode gives you ultimate privacy protection!"

### ❌ Avoid This (No Marketing Fluff)
- **Over-promising**: Ultimate, Perfect, Zero Risk, 100%.
- **Marketing Adjectives**: Shocking, Revolutionary, Redefining, From Scratch.
- **Inducing Punctuation**: Avoid continuous exclamation marks (!!) or Emoji bombing.
- **Overused Metaphors**: "Data Fortress", "Privacy Great Wall" (Just state the technical principle directly).

## 🏗️ Standard Document Structure

A standard whitepaper document should contain the following parts:

### 1. Title (H1)
Clear and explicit topic, e.g., `# ⚠️ API Key Usage & Limits`.

### 2. Summary/Intro
One sentence explaining the purpose of this document.

```markdown
This document details LiuliX's data privacy protection mechanism and sanitization policy.
```

### 3. Core Content (H2 - H3)
- Use **Tables** to compare different modes (e.g., Local vs. Cloud).
- Use **Code Blocks** to show configuration examples or JSON responses.
- Use **Mermaid Charts** (Optional) to explain complex flows, but keep them simple.

### 4. Visual Emphasis (Callouts)
Use blockquotes or Emoji lists to emphasize key information:

```markdown
- ✅ **Recommended**: Use Ollama Local Mode
- ⚠️ **Note**: Cloud Mode consumes quota
- ❌ **Prohibited**: Using Trial Key in production environment
```

### 5. FAQ
Anticipate user questions in Q&A format, especially regarding privacy and costs.

### 6. Related Documents
Provide cross-links to form a knowledge network.

---

## 📏 Formatting Rules

1. **Mixed Language**: Add spaces between distinct languages (e.g. English and Chinese if mixed).
   - Correct: Use Ollama Local Model
2. **Numbers & Units**: Add spaces around numbers.
   - Correct: Limit 20 calls
3. **Code Reference**: Use inline code blocks \`\` to wrap key terms, config items, file paths.
   - Example: Enable `Use Local Model` in `Settings`.
4. **Links**: Use relative paths to reference other whitepaper documents.

---

## 🔍 Data Privacy Special Regulations

When describing data privacy, strictly adhere to the following terms:

- **Local Mode** = **Fully Offline** / **Zero Cloud Dependency**
- **Cloud Mode** = **Data Upload** (Even if sanitized)
- **Auto Sanitize** = **Metadata Only**
- **Raw Data** = **Sampled Data**

**Strictly Prohibited** to use ambiguous descriptions that mislead users into thinking Cloud Mode is also offline.

---

## 🛠️ Maintenance Process

1. **Change Sync**: Sync documentation within 24 hours after code logic changes (e.g., quota policy adjustment).
2. **Multi-language**: Currently **Chinese** is primary, future support for English versions must maintain consistent structure.
3. **Version Number**: Note the last update date at the bottom of the document.
